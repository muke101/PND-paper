\RevB{4} \textbf{Applicability beyond Store Sets.} It is correct that most of the IPC gain comes from reducing table aliasing, which is specific to direct-mapped tables such as Store Sets. However, fundamentally PG-MDP reduces the predictor working set (see Fig. \ref{fig:lookups}), with reduced aliasing being how this manifests for Store Sets specifically. Comparing to industry predictors found in \cite{ssbench}, there are other direct-mapped predictors that would benefit this way. Other designs, such as the 21-entry fully-associative predictor in Apple's efficiency core, already spend a large portion of their budget on preventing aliasing. In these cases we expect a smaller immediate IPC gain, which we have not been able to measure, but envision the applicability of PG-MDP to be enabling predictor co-design, where the benefits of filtering independent loads is delivered in software so the hardware may focus on accurately predicting truly dependent loads. Section \ref{sec:readports} also aligns with this idea.

\RevB{5} \textbf{Other Store Set optimization techniques.} We have not evaluated Onder and Gupta's scheme \cite{onder}. \RevD{1} details our expanded evaluation (which does include your requested comparison with \cite{storedistance}) where we prioritized breadth beyond Store Sets variants, of which we already evaluate two.

\RevBLink{6} \textbf{How many memory units.} The modeled processor has 6 memory functional units (AGU), used for both reads and writes, but the number of memory operations per cycle are limited by L1D ports. We have added this to Table~\ref{table:cpu-models} and Section~\ref{sec:models}.

\RevDLink{1} \textbf{Comparison to other approaches.} We have extended the evaluation to include comparison against more MDP techniques. This includes blind speculation, no speculation, the original Store Sets \cite{storesets}, XS Store Sets filtered with a load-wait table~\cite{kessler1999alpha}, and an idealized reproduction of \cite{storedistance}. \RevE{1} \textbf{Concentration of IPC Gains.} We agree gains are concentrated in a minority of workloads. This is a property of MDP in general (as Reviewer C also notes), and not of PG-MDP specifically. Any MDP technique can only improve performance where load instruction scheduling falls on the critical path, such as interpreters ($600.perlbench\_s$) or video encoding ($625.x264\_s$). For these cases we reiterate that PG-MDP captures the majority of available performance (Fig. \ref{fig:ssit_sweep}, Fig. \ref{fig:mdp-comp}). Other workloads, for instance GAPBS \cite{gapbs} which is dominated by memory latency, change the available headroom, not how much of it PG-MDP recovers.
%Our new evaluation of GAPBS (Section \ref{sec:gapbs}) presents a case where all workloads are dominated by memory latency and MDP has no opportunity to improve performance. Here, PG-MDP is neutral (+0.015\%) while still reducing queries by 62\%. Therefore a different workload class changes the available headroom, not how much of it PG-MDP recovers.

\RevE{2} \textbf{Cost of Scaling the MDP Instead.} We agree that a sufficiently large MDP has less need for PG-MDP. This is why we target a class of cores that have been demonstrated to allocate as little as 50-100 bytes of storage for MDP \cite{ssbench}. A design-space exploration of the relative area \& power overhead of scaling the MDP against opportunity cost in the total core would be useful, but for the purposes of this work we aim to deliver performance at the budget vendors have already determined to be optimal for their design.
